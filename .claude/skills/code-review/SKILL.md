# Multi-Agent Code Review

3 体のレビューエージェントが並列にレビューし、親 Claude がとりまとめる反復レビュープロセス。ラウンド 2 以降は反証役を加え、指摘の精度を上げる。

## レビューエージェント

### 常時起動（ラウンド 1 から並列）

| エージェント | 種別 | 専門領域 |
|---|---|---|
| **ダ・ヴィンチちゃん — Logic Reviewer** | 専任サブエージェント（`.claude/agents/da-vinci-chan.md`） | バグ・ロジックエラー・エッジケース・**並行性と競合**・**数値と時刻の境界**・テスト網羅性と**安定性**・エラーハンドリング・データ整合性・AI 特有の誤り（hallucinated API・形骸テスト等） |
| **ギルガメッシュ — Security & Design Reviewer** | 専任サブエージェント（`.claude/agents/gilgamesh.md`） | セキュリティ・認証/認可・マルチテナント分離・**ログ衛生とプライバシー**・パフォーマンス・設計・**可読性と保守性**・命名規約・**依存の追加**・破壊的変更・AI 生成コードっぽさ（独自用語・過剰コメント・命名ブレ等） |
| **エミヤ — Integration & Ops Reviewer** | 専任サブエージェント（`.claude/agents/emiya.md`） | 追随漏れ（呼び出し側・登録一覧・テスト・ドキュメント）・二重管理・冪等性・巻き戻し可否・**リソースの解放漏れ**・**外部依存の壊れ方**・**本番適用コスト**・**不要物の回収漏れ**・観測可能性・仕様の欠落 |

3 体は**見る対象**で分業している。ダ・ヴィンチちゃんとギルガメッシュは変更ファイルの**中身**を精読する。エミヤはその逆で、**変更されていないファイル**（追随すべきだったのに手が入っていない箇所）と**適用後の時間軸**（再実行・部分失敗・巻き戻し）を見る。

上記のうち、並行性・競合（ダ・ヴィンチちゃん）は**差分が該当する場合のみ深掘りする条件付き観点**である（共有状態・非同期処理・トランザクション・ロック・並行起動されうるスクリプトに触れているとき）。それ以外はエージェント定義側で「常時適用」として扱われるため、スキルから重点観点として渡す必要はない。

### ラウンド 2 以降に追加

| エージェント | 種別 | 役割 |
|---|---|---|
| **モードレッド — Devil's Advocate** | 専任サブエージェント（`.claude/agents/mordred.md`） | 統合レポートの各指摘を現物のコードで検証し、誤検知・重要度過大・スコープ外を潰す。新規指摘の探索は行わない |

ラウンド 1 では検証対象の指摘が存在しないため起動しない。したがって 1 ラウンドで終了する場合、モードレッドは起動しない。

### オプション（明示要求時のみ）

| エージェント | 種別 | 専門領域 |
|---|---|---|
| **Codex Reviewer** | 汎用サブエージェント（`model: haiku` 指定、内部で codex CLI 実行） | 全観点の総合レビュー（外部モデルによる独立視点） |

ユーザーが「Codex も」「codex 込みで」「4 体で」等と明示的に要求したときだけ追加する。**要求がなければ起動しない**（`codex` が PATH にあっても自動起動しない）。

各エージェントの役割・手順・出力形式はエージェント定義側に記述済み。スキルからは動的コンテキスト（リポジトリ情報・仕様コンテキスト・重点観点・前ラウンド結果）のみを `prompt` で渡す。AI 生成コード特有の観点（カテゴリ: AISmell）はダ・ヴィンチちゃん / ギルガメッシュの定義に「常時適用」として記述済みのため、スキルから渡す必要はない。

## 起動条件

### パターン A: ユーザーリクエスト

以下のようなフレーズで起動する:

- 「レビューして」「コードレビュー」「コードを確認して」「差分を見て」
- 「review」「code review」
- 「3ラウンドでレビューして」（ラウンド数指定付き）

### パターン B: セルフレビュー

Claude Code がコードを変更した後、品質チェックのために自発的に実行する。以下の場面で実行する:

- 複数ファイルにまたがる変更を行った後
- リファクタリングを実施した後
- ユーザーの指示が曖昧で意図通りの実装か確信がないとき

---

## ラウンド数

- ユーザーが「Nラウンドでレビューして」のように指定した場合、N ラウンド実行する
- 指定なしの場合は差分規模で決める（1 ラウンドあたり 3〜4 エージェントが動くため、複数ラウンドは従量課金下で高コストになる）:
  - 差分が小さい場合（目安: 変更 100 行以下）は **1 ラウンド**
  - それ以外は **2 ラウンド**
- 全ラウンド完了後、追加ラウンドを実施するかユーザーに確認する。1 ラウンドで Critical/High の指摘が出た場合は修正後の再レビュー（+1 ラウンド）を推奨する

> **1 ラウンドで終わる場合の注意**: モードレッド（反証役）はラウンド 2 以降にのみ参加するため、1 ラウンドで終了すると指摘の誤検知チェックが入らない。1 ラウンドで Critical / Warning の指摘が出た場合は、追加ラウンドの確認時に「モードレッドによる反証が入っていない」ことを添えて推奨する。

## 実行手順

### ステップ 1〜2: 前提確認・ベースブランチの特定

```bash
~/.claude/skills/code-review/scripts/check-prereqs.sh
```

出力される `CODEX=` `BASE=` 行をパースする。

- `CODEX=available` / `CODEX=unavailable`: **Codex を明示要求されたときだけ参照する**。要求されているのに `unavailable` の場合は「codex が見つからないため内製 3 体で続行する」旨をユーザーに伝える。要求がなければこの行は無視する（Codex は自動起動しない）
- `BASE=main` / `BASE=master`: そのブランチを BASE として以降のステップで使用する
- `BASE=`（空）: main/master どちらも存在しないため、未コミット変更のみを対象とする

### ステップ 3: 変更内容の把握

```bash
git diff --name-only <BASE>...HEAD
git diff --name-only HEAD
git ls-files --others --exclude-standard
git log --oneline <BASE>..HEAD
```

変更ファイルが 0 件かつ未コミット変更もない場合は「レビュー対象の変更がありません」と伝えて終了する。

### ステップ 4: 関連ファイルの特定

変更ファイル一覧をもとに、以下の関連ファイルを特定する:

1. **テストファイル**: `*_test.*`, `*.spec.*`, `test_*.*`, `__tests__/` 配下
2. **設定ファイル**: `package.json`, `tsconfig.json`, `Makefile`, `Dockerfile` 等
3. **インポート元**: 変更されたモジュールを import/require しているファイル

```bash
git grep -l "import.*<変更ファイル名>" -- '*.ts' '*.tsx' '*.js' '*.jsx'
git grep -l "from ['\"].*<変更モジュール名>['\"]" -- '*.py'
```

### ステップ 5: 仕様ドキュメントの確認

レビューの精度を上げるため、変更の背景となる仕様ドキュメント（Plan Doc、Specification、Design Doc、RFC 等）の有無を確認する。

#### 5.1 既存コンテキストの確認

現在の会話内で以下のいずれかが既に共有されているか確認する:

- Plan Doc / 設計ドキュメント
- 仕様書 / Specification
- Issue / チケットの説明
- RFC / ADR

共有済みであれば、その内容をステップ 5.2 の「仕様コンテキスト」として使用する。

#### 5.2 未共有の場合: ユーザーに確認

会話内に仕様ドキュメントが見当たらない場合、ユーザーに確認する:

- 「この変更に関する仕様ドキュメント（Plan Doc、Spec 等）はありますか？」
- ある場合: ファイルパスまたは URL を教えてもらい、Read ツールや WebFetch ツールで内容を取得する
- ない場合: コミットメッセージとコード差分のみを根拠にレビューを進める

> **パターン B（セルフレビュー）の場合**: 会話内にタスクの指示内容が既にあるため、それを仕様コンテキストとして使用する。ユーザーへの確認は行わない。

#### 5.3 サブエージェントへの受け渡し

仕様コンテキストが取得できた場合、各サブエージェントのプロンプトに `## 仕様コンテキスト` セクションとして追加する。これにより各エージェントは「仕様に対して実装が正しいか」の観点でもレビューできる。

---

### ステップ 6: レビュー観点の読み込みと分配

`references/` ディレクトリ配下のプロジェクト固有レビュー観点ファイルを読み込む。社内プロジェクト向けの観点は git 管理外の `references/private/` に置かれているため、両方を探索する。

```bash
ls ~/.claude/skills/code-review/references/ ~/.claude/skills/code-review/references/private/ 2>/dev/null
```

現在の作業ディレクトリのプロジェクト名に一致するファイルがあれば Read ツールで内容を読み込み、以下のマッピングに従って各エージェントのプロンプトに含めるセクションを抽出する。

#### ダ・ヴィンチちゃん (Logic) に渡すセクション

- エラーハンドリング
- テスト関連
- SQLC クエリ
- フォーム実装・Custom Hook
- LIKE パターン
- Valkey 操作

#### ギルガメッシュ (Security & Design) に渡すセクション

- セキュリティ全般（入力検証・SQL インジェクション・認可・秘匿情報）
- 認証ロジックのバイパス
- マルチテナント分離（tenant_id）
- IAM 権限
- URL 構築
- 命名・コメント・用語規約
- 破壊的変更（後方互換性の判断）
- 既存 UI との整合性
- インフラ（既存リソースへの影響）

#### エミヤ (Integration & Ops) に渡すセクション

「〜漏れ」「〜整合」「対称性」「規約への追随」型の項目を渡す。

- ドキュメント整合（CLAUDE.md / AGENTS.md / README と実装の乖離）
- 配布・登録一覧への追随（`scripts/link.sh` の `LINKS`、`settings.json` の `permissions.allow`）
- 同一パスの二重管理（`LINKS` と home-manager の重複）
- DB マイグレーション（up/down の対称性・逆順）
- RLS の有効化・ポリシー作成の漏れ
- API 定義（proto / OpenAPI 等）の必須 option・アノテーションの設定漏れ
- 設計判断への参照コメント（ADR 等）の付与漏れ
- i18n の翻訳コンポーネントでの囲み漏れ・キーの追加漏れ
- E2E / シナリオテストの必須ラベル・分類の付与漏れ
- 生成コード・スキーマ・型定義と実装の不一致
- shell スクリプトの再実行時の挙動

> **プロジェクト固有の名前をここに書かない**: 具体的な option 名・ラベル名・ADR 番号の書式・独自ヘルパー名は `references/` 配下（社内プロジェクトのものは git 管理外の `references/private/`）が持つ。この SKILL.md には汎用の項目名だけを書き、実際の識別子は読み込んだ references の該当セクションをそのまま渡すことで各エージェントに伝える。

#### 該当しない項目の扱い

- references 側にタグ（`[Logic]` / `[Design]` / `[Ops]`）がある場合はタグに従う
- 上のリストにもタグにも該当しない項目は、内容から最も近い担当に渡す。判断に迷う項目は複数のエージェントに渡してよい（重複した指摘はステップ 7.2 でマージされる）

#### モードレッド (Devil's Advocate) に渡す観点

**渡さない。** 任務は既存指摘の検証であり、新たな観点からの探索を行わせないため。渡すのは統合レポートとリポジトリ情報のみ。

#### Codex Reviewer に渡す観点（明示要求時のみ）

**全セクション**を `--title` 経由で要約して渡す。

### ステップ 7: マルチラウンドレビューの実行

指定ラウンド数（デフォルト 2）だけ以下を繰り返す。

#### 7.1 各エージェントの並列起動

> **重要: 並列実行の指示**
>
> そのラウンドで起動する全エージェントを **必ず同一メッセージ内の複数ツールコールとして同時に発行すること**。
> 1 つずつ順番に起動してはならない。複数のツールコールを 1 回のレスポンスに含めることで並列実行される。
>
> - ラウンド 1: ダ・ヴィンチちゃん、ギルガメッシュ、エミヤ（+ 明示要求時のみ Codex Reviewer）
> - ラウンド 2 以降: 上記への SendMessage + モードレッドの起動を、すべて同一メッセージ内で発行する

> **重要: 新規 spawn はラウンド 1 のみ（モードレッドを除く）**
>
> Agent ツールでの起動は **ラウンド 1 のみ**。ラウンド 2 以降は、ラウンド 1 で起動した各エージェントに **SendMessage** で統合レポートと再レビュー指示を送る。
> 新規 spawn はコールドスタートとなり、各エージェントが diff・変更ファイルを一から読み直すコストを払うことになる。SendMessage なら読込済みのコンテキストを再利用できる。
>
> **例外はモードレッドのみ**: ラウンド 1 では起動していないため、ラウンド 2 で Agent ツールで新規 spawn する。ラウンド 3 以降はモードレッドにも SendMessage を使う。

---

##### ダ・ヴィンチちゃん — Logic Reviewer

Agent ツールで `subagent_type: "da-vinci-chan"` を指定して起動する。役割・レビュー手順・出力形式はエージェント定義に記述済みのため、`prompt` には以下の動的コンテキストのみを含める:

```
## リポジトリ情報
- パス: <作業ディレクトリの絶対パス>
- ベースブランチ: <BASE>
- 現在のブランチ: <ブランチ名>
- 変更ファイル: <ファイル一覧>
- 関連ファイル: <ステップ4の結果>
- コミット履歴:
<git log --oneline の結果>

## 仕様コンテキスト
<ステップ5で取得した仕様ドキュメントの内容。なければこのセクションを省略>

## 重点観点
<ステップ6で抽出したダ・ヴィンチちゃん向けセクション>
```

**ラウンド 2 以降は、新規 spawn せず SendMessage で同一エージェントに以下のみを送る:**

```
## 前ラウンドの統合結果
<前ラウンドの統合レポート全文>

上記の統合結果を踏まえ、以下を重点的に確認してください:
- 他のレビューアーが見落としている問題がないか
- 既存の指摘に補足すべき点がないか
新たな発見がなければ「追加指摘なし」と明記すること。
```

> 誤検知の検証はモードレッド（反証役）の担当のため、レビュアーへの再レビュー指示には含めない（同じ検証を 3 重に走らせても精度は上がらず、コストだけが増える）。既存指摘が誤りだと気付いた場合に補足として述べるのは妨げない。

##### ギルガメッシュ — Security & Design Reviewer

Agent ツールで `subagent_type: "gilgamesh"` を指定して起動する。`prompt` の構成はダ・ヴィンチちゃんと同じ（リポジトリ情報・仕様コンテキストは同一内容、重点観点のみギルガメッシュ向けセクションに差し替える）。

**ラウンド 2 以降はダ・ヴィンチちゃんと同様、SendMessage で同じ追加コンテキストを送る。**

---

##### エミヤ — Integration & Ops Reviewer

Agent ツールで `subagent_type: "emiya"` を指定して起動する。`prompt` の構成はダ・ヴィンチちゃんと同じ（リポジトリ情報・仕様コンテキストは同一内容、重点観点のみエミヤ向けセクションに差し替える）。

エミヤの手順は「変更されていないファイルを Grep で探す」ため、**リポジトリ情報の「変更ファイル」「関連ファイル」の一覧が探索の起点になる**。ステップ 3・4 の結果は省略せずに全件渡すこと。

**ラウンド 2 以降はダ・ヴィンチちゃんと同様、SendMessage で同じ追加コンテキストを送る。**

---

##### モードレッド — Devil's Advocate（ラウンド 2 以降のみ）

**ラウンド 1 では起動しない。** ラウンド 2 で Agent ツールに `subagent_type: "mordred"` を指定して新規 spawn し、ラウンド 3 以降は SendMessage で同一エージェントに送る。

ラウンド 2 での起動時、`prompt` には以下を含める（重点観点は渡さない）:

```
## リポジトリ情報
- パス: <作業ディレクトリの絶対パス>
- ベースブランチ: <BASE>
- 現在のブランチ: <ブランチ名>
- 変更ファイル: <ファイル一覧>

## 仕様コンテキスト
<ステップ5で取得した仕様ドキュメントの内容。なければこのセクションを省略>

## 検証対象の統合レポート
<前ラウンドの統合レポート全文>

上記の全指摘について判定を出してください。Upheld も省略しないこと。
```

**ラウンド 3 以降は SendMessage で以下のみを送る:**

```
## 検証対象の統合レポート（ラウンド N）
<最新の統合レポート全文>

前回判定済みの ID については、指摘内容が更新されている場合のみ再判定してください（変わっていなければ「前回判定を維持」と記す）。
新規 ID（前回の判定対象になかったもの）は全件判定してください。
```

##### Codex Reviewer（明示要求時のみ）

**ユーザーが明示的に要求していない場合、このエージェントは起動しない。** 要求された場合のみ、Agent ツールで起動する（専任エージェント定義はなく汎用サブエージェントを使う）。**必ず `model: haiku` を指定すること**（このエージェントの仕事はスクリプト実行と出力の整形のみで、レビュー自体は codex 側が行う。モデルを親から継承すると高価なモデルがスクリプトランナーをやることになる）。サブエージェント内で `scripts/codex-review.sh` を実行させる。`prompt` に以下の内容を含める:

```
あなたは Codex Reviewer です。codex-review.sh スクリプトを使ってコードレビューを実行し、結果を報告してください。

## スクリプトの実行

以下のコマンドを実行してください:

~/.claude/skills/code-review/scripts/codex-review.sh "<BASE>" "<TITLE>"

引数:
- 第1引数 (BASE): <ベースブランチ名。ベースブランチがない場合は空文字 "">
- 第2引数 (TITLE): "<ブランチ名> | 変更概要: <概要> | 関連ファイル: <一覧> | 観点: <全セクションの要約>"

スクリプトが committed/uncommitted の判定と codex review の実行を行います。

## 仕様コンテキスト
<ステップ5で取得した仕様ドキュメントの内容。なければこのセクションを省略>

## レビュー観点（全観点）
<references ファイルの全内容>

上記に加え、AI 生成コード特有の問題にも注意すること: 既存コードベースにない独自用語の導入、コメントと識別子の不一致・不要な言い換え、命名の一貫性のブレ、過剰な自明コメント、存在しない API の呼び出し、実装をなぞるだけの形骸化したテスト、エラーを黙って握りつぶす fallback。

## 出力形式
codex の出力をそのまま含めた上で、以下の形式に整理して報告すること:
- **ファイル:行番号**
- **重要度**: Critical / Warning / Info
- **カテゴリ**: 適切なカテゴリ
- **指摘内容**: 具体的な問題の説明
- **修正案**: あれば具体的なコード例

指摘がない場合は「指摘なし」と明記すること。
```

**ラウンド 2 以降は、新規 spawn せず SendMessage で同一エージェントに以下のみを送る:**

```
## 前ラウンドの統合結果
<前ラウンドの統合レポート全文>

上記の統合結果を踏まえ、TITLE 引数に主要な Critical/Warning 項目のサマリーを追加して codex-review.sh を再実行してください。
TITLE が長くなりすぎる場合は Critical 項目のみに絞ること。
他のレビューアーが見落としている問題がないか重点的に確認してください。
新たな発見がなければ「追加指摘なし」と明記すること。
```

#### 7.2 統合フェーズ

全エージェントの結果が返ってきたら、親 Claude が以下の手順で統合する:

1. **重複排除**: 同一ファイル・同一箇所への同内容の指摘をマージし、発見したエージェントを併記する
2. **重要度の調整**: 複数エージェントが独立して同じ問題を指摘した場合、信頼度が高いため重要度を 1 段階引き上げる（Info → Warning、Warning → Critical）
3. **モードレッドの判定を適用**（ラウンド 2 以降のみ。**必ず手順 2 の後に行う**。引き上げと引き下げの順序が逆になると、反証済みの指摘が重複一致で引き上げられて残ってしまう）
4. **カテゴリ分類**: 統一カテゴリに整理する
5. **ID 付与**: 各指摘に優先度別の連番 ID（`P1-1` = Critical、`P2-1` = Warning、`P3-1` = Info）を付与する。前ラウンドから継続している指摘には同じ ID を引き継ぎ、新規指摘には次の連番を割り振る（欠番があっても詰め直さない）
6. **統合レポートの作成**: 次ラウンドの入力として使用する統合レポートを作成する

##### モードレッドの判定の適用ルール

| 判定 | 統合レポートへの反映 |
|---|---|
| **Refuted** | 「却下」セクションに移し、Critical/Warning/Info からは外す。ID は変えない。TaskCreate 済みなら `deleted` にする |
| **Overstated** | 重要度を推奨値まで下げる。ID は引き継ぐ（P1-1 が Warning に下がっても ID は P1-1 のまま。ID は優先度ではなく指摘の識別子として扱う） |
| **OutOfScope** | 「却下」セクションに移し、理由を「既存の問題（この差分の対象外）」と記す |
| **Upheld** | 現状維持 |

**親 Claude は最終判断者である。** 以下の場合はモードレッドの判定を採用しない（採用しなかった旨と理由を統合レポートに 1 行で残す）:

- 却下・格下げの根拠が file:line やコマンド結果で示されておらず、憶測にとどまる
- セキュリティ上の欠陥を「既存コードベースの慣習と同型」を理由に格下げしている（既存が一様に危険なだけであり、格下げの根拠にならない）
- 元の指摘の内容を取り違えた上で反証している

統合レポートの形式:

```markdown
## 統合レポート（ラウンド N）

### Critical (P1)
- P1-1: ファイル:行 — 指摘内容 [発見: ダ・ヴィンチちゃん, ギルガメッシュ]
- P1-2: ...

### Warning (P2)
- P2-1: ファイル:行 — 指摘内容 [発見: エミヤ]
- P2-2: ファイル:行 — 指摘内容 [発見: ギルガメッシュ / 格下げ: モードレッド（到達不能）]

### Info (P3)
- P3-1: ファイル:行 — 指摘内容 [発見: ギルガメッシュ]
- P3-2: ...

### 却下（モードレッドの反証により除外）
- P2-3: ファイル:行 — 指摘内容 / 却下理由: <根拠の要約>
- P3-4: ファイル:行 — 指摘内容 / 対象外理由: 既存の問題（この差分の対象外）
```

却下セクションは次ラウンドの入力にも残す（同じ指摘が再提出されたときに、親 Claude が既に反証済みだと判断できるようにするため）。

次ラウンドのエージェントプロンプトやユーザーとのやり取りでは、指摘を指す際にこの ID（`P1-1` 等）で参照する。

> **注意**: この ID は Claude Code とユーザーのやり取りを円滑にするための一時的な識別子であり、コードや Issue のトラッキング ID ではない。指摘対応をコミットする際、**コミットメッセージに ID（`P1-1` 等）を含めてはならない**。コミットメッセージは通常どおり変更内容そのもの（何をなぜ直したか）を記述する。

#### 7.3 次ラウンドへの遷移

最終ラウンドでなければ、統合レポートを次ラウンドの入力として渡す（7.1 の「ラウンド 2 以降」の指示に従う）。

- レビュアー 3 体（+ Codex）には SendMessage で送る
- モードレッドは、ラウンド 2 では Agent ツールで新規 spawn、ラウンド 3 以降は SendMessage で送る
- これらをすべて**同一メッセージ内で発行**する

---

### ステップ 8: 最終レポートの出力

全ラウンド完了後、以下の形式で最終レポートを出力する。ID は 7.2 で付与したものをそのまま引き継ぐ。

```markdown
## コードレビュー結果（全 N ラウンド完了）

### Critical（要対応） P1
- [ ] P1-1: ファイル:行 — 指摘内容 [発見: ダ・ヴィンチちゃん, ギルガメッシュ]
- [ ] P1-2: ...

### Warning（検討推奨） P2
- [ ] P2-1: ファイル:行 — 指摘内容 [発見: エミヤ]
- [ ] P2-2: ...

### Info（参考） P3
- P3-1: ファイル:行 — 指摘内容 [発見: ギルガメッシュ]
- P3-2: ...

### 却下（反証により除外）
- P2-3: ファイル:行 — 指摘内容 / 却下理由: <根拠の要約>

### 統計
- Critical: N 件 / Warning: N 件 / Info: N 件 / 却下: N 件
- ラウンド間の推移: ラウンド1 → ... → 最終ラウンド
```

却下セクションは、モードレッドが参加したラウンドがあり却下された指摘が 1 件以上ある場合のみ出力する（0 件なら省略する）。

最終レポート出力後、Critical (P1) と Warning (P2) の指摘を「タスク登録による対応状況管理」に従って TaskCreate で登録する。却下された指摘は登録しない。

### ステップ 9: 追加ラウンドの確認

タスク登録後、ユーザーに「追加ラウンドを実施しますか？」と確認する。

- 「はい」「追加で」等の場合: ステップ 7 に戻り 1 ラウンド追加実行する（再度確認も行う）
- 「いいえ」の場合: レビュー終了

確認時に、追加ラウンドで得られるものを添える:

- **1 ラウンドで終わった場合**: 追加ラウンドではモードレッド（反証役）が参加し、既存の指摘の誤検知チェックが入る
- **Codex を起動していない場合**: 「Codex（外部モデル）を加えることもできます」と 1 行で添える（こちらから起動はしない）

## タスク登録による対応状況管理

対応が必要な指摘は TaskCreate でタスク登録する。タスクは PostToolUse フック
(`sync-tasks-to-obsidian.sh`) が Obsidian の対応状況ノートへ自動同期するため、
スキル側で Obsidian を直接操作してはならない（更新漏れと obsidian CLI の
多重起動問題を避けるための設計。レポート全文はセッションログノートに残る）。

- **subject**: `P1-1: ファイル:行 — 指摘内容の要約`（ID プレフィックス必須。Obsidian 側で指摘とタスクを突き合わせるキーになる）
- **登録対象**: パターン A では最終レポートの Critical (P1) / Warning (P2)。パターン B では【修正する】に分類した指摘。Info (P3) や【対応不要】は登録しない
- **状態遷移**: 指摘への対応に着手したら `in_progress`、解消を確認したら `completed`。誤検知と判明した指摘は `deleted`
- 追加ラウンドで新規指摘が出たら追加登録する。登録済みの ID を再登録しない

## パターン B: セルフレビュー

セルフレビューでは **1 ラウンド** のマルチエージェントレビューを実行し、その後修正ループに入る。

1. ダ・ヴィンチちゃん、ギルガメッシュ、エミヤを並列起動（1 ラウンドのみ。Codex は明示要求時のみ追加）
2. 統合レポートを作成し、各指摘に ID（`P1-1` 等）を付与する
3. **モードレッドを起動して指摘を検証する**（Agent ツールで新規 spawn。統合レポートを渡す）

   > パターン A ではモードレッドはラウンド 2 以降に参加するが、パターン B では**修正に着手する前**に起動する。誤検知に基づいて自分のコードを書き換えてしまうと、修正そのものが無駄になるうえ、書き換えた後では反証の機会が失われるため。

4. モードレッドの判定を 7.2 の適用ルールで反映した上で、ID ごとに指摘を分類する:
   - **【修正する】**: バグ、論理エラー、要件の未充足、セキュリティ問題 → 修正を実施
   - **【対応不要】**: スコープ外、既存コードの規約に沿っている、トレードオフを考慮した上での設計判断、モードレッドが根拠付きで却下した指摘
5. 【修正する】に分類した指摘を TaskCreate で登録する（「タスク登録による対応状況管理」を参照。登録済みの ID は再登録しない）
6. 修正すべき指摘がある場合:
   a. 指摘のタスクを TaskUpdate で `in_progress` にして修正を実施する（コミットする場合、コミットメッセージに ID を含めない。7.2 の注意を参照）
   b. SendMessage で全エージェント（レビュアー 3 体 + モードレッド）に修正内容の要約を送り、diff を再確認させて再レビュー（新規 spawn しない。同一メッセージ内で並列発行）
   c. 解消が確認できた指摘のタスクを `completed` にする。継続している指摘には元の ID を引き継ぎ、4 に戻る
7. 全指摘が解消 or 対応不要になったらループ終了
8. ユーザーに以下を報告する（いずれも ID を明記する）:
   - 修正した内容の一覧（何をどう直したか）
   - 対応不要と判断した指摘の一覧と理由
   - 最終レビュー結果（問題なし or 残課題あり）

## エラーハンドリング

| 状況 | 対応 |
|------|------|
| Codex を明示要求されたが `codex` が見つからない | 内製 3 体で実行（Codex Reviewer をスキップ）。ユーザーに通知する |
| Codex の要求がない | 内製 3 体で実行する。`codex` の有無に言及しない（オプション機能であり、毎回案内すると雑音になる） |
| ベースブランチが見つからない | 未コミット変更のみを対象にレビュー |
| 変更が 0 件 | 「レビュー対象の変更がありません」と伝えて終了 |
| サブエージェントがエラー | 残りのエージェント結果で統合を続行。エラーを報告する |
| codex がタイムアウト | 内製 3 体の結果で統合し、codex スキップを報告 |
| モードレッドがエラー / 起動失敗 | 反証なしで統合を続行する。**指摘を却下・格下げしてはならない**（未検証のまま統合する）。反証が入っていない旨を最終レポートに明記する |
| モードレッドが全件 Refuted を返した | 各判定の根拠を確認する。根拠が薄いものは 7.2 の「採用しない」条件に従って却下を取り消す（全件却下は反証の暴走を疑う） |
